NFT数字藏品交易平台的设计与实现

说明：本文档依据 D:\AStudy\NFT 项目源码、数据库 E-R 图、系统流程图以及已有论文初稿资料重新整理撰写。项目当前采用前端、后端、智能合约与部署脚本分层组织，系统名称在前端中体现为 Nova NFT Market。文档内容重点围绕系统设计目标、需求分析、总体架构、数据库设计、智能合约设计、后端实现、前端实现、核心业务流程、安全与测试等方面展开。

一、研究背景与系统建设目标

随着数字内容生产工具和传播平台的发展，图片、音乐、视频等数字作品的创作门槛持续降低。过去，一个作品要进入市场，往往需要较高的发行成本、平台审核成本和版权登记成本；现在，创作者只要有一台电脑或一部手机，就可以完成内容生产并快速发布。问题也随之出现：数字文件可以被无损复制，传播过程很快，但作品的归属、交易历史和稀缺性却很难仅靠传统数据库来证明。也就是说，数字作品越容易传播，越需要一种可靠机制来回答“这个作品是谁发布的、现在归谁、经历过哪些交易”这些基础问题。

NFT，即非同质化通证，为数字内容确权提供了一种新的技术路径。与普通同质化代币不同，每一个 NFT 都具有唯一编号和独立元数据，可以映射某个具体数字作品。通过 ERC-721 等标准，NFT 能够在链上记录所有权关系，并通过交易事件体现资产流转过程。区块链的公开、可追溯和难篡改特征，使 NFT 不再只是一个平台内部的展示卡片，而是可以被钱包、浏览器、合约和应用共同识别的数字资产凭证。

不过，真正做一个可用的 NFT 数字藏品交易平台，并不是写一个合约就结束了。合约负责链上的确权与交易，但用户还需要登录、上传作品、浏览市场、筛选藏品、查看详情、购买资产、管理个人资料和查询历史订单。媒体文件也不能直接全部放到链上，因为图片、音频和视频体积较大，链上存储成本很高。因此，完整平台需要形成“链上负责可信交易，链下负责高频业务和用户体验”的协同结构。本项目正是围绕这个思路展开。

本系统的总体目标，是实现一个面向数字藏品场景的 NFT 交易平台。用户可以通过浏览器钱包完成身份认证，可以上传图片、音频或视频作品，可以将作品媒体和元数据上传到 IPFS，可以调用智能合约完成 NFT 铸造、上架、下架和购买，也可以在个人中心查看当前持有、历史买入和历史卖出记录。说得直白一点，这个项目不只是“把一个图片 mint 到链上”，而是尽量把从创作到交易、从展示到资产管理的闭环都跑通。

从工程角度看，项目采用 frontend、backend、contracts、hardhat 四个主要目录组织源码。frontend 使用 Next.js 14、React 18、ethers.js 与 Tailwind CSS，承担用户界面、钱包交互和链上操作封装；backend 使用 Go 1.22、Gorilla Mux、GORM 与 MySQL，承担 REST API、认证、NFT 数据、订单、上传和 IPFS 服务；contracts 和 hardhat 承担 Solidity 合约源代码、编译、部署和测试环境配置。当前一方源码统计约 7823 行，其中后端约 1943 行，前端约 5498 行，合约约 175 行，Hardhat 配置与部署相关代码约 207 行。这一规模说明项目已经不是单文件演示，而是具备较完整分层的应用原型。

二、系统需求分析

系统需求可以从用户需求、业务需求、数据需求和非功能需求四个层面分析。首先，在用户需求层面，平台面向普通数字藏品创作者和购买者。一个用户在不同场景下可以具有多重身份：当他上传作品时，他是创作者；当他上架作品时，他是卖家；当他浏览并购买其他作品时，他又是买家。这种设计比固定划分“管理员、卖家、买家”更贴近 NFT 市场，因为同一个钱包地址在链上本来就可以自由持有、出售和购买资产。

平台需要提供钱包登录能力。传统账号密码登录可以满足一般 Web 应用需要，但在 NFT 场景中，资产所有权最终与钱包地址绑定。如果平台仍然主要依赖用户名和密码，就会出现链上身份与平台身份脱节的问题。因此，本项目采用钱包签名登录：后端为钱包地址生成随机 nonce，前端要求用户用钱包签名，后端根据签名恢复地址并校验是否与请求地址一致。认证成功后，系统签发 JWT，前端在后续 API 请求中携带该 token。这样既避免了用户上传密码，也能证明当前用户确实控制该钱包地址。

平台需要提供 NFT 创建能力。用户进入创建页后，可以填写作品名称、描述、分类、价格和版税信息，并上传主媒体文件。分类包括艺术、音乐、视频和其他。不同分类对应不同媒体约束，例如艺术类主要对应图片，音乐类对应音频，视频类对应视频，其他类可以兼容更多格式。对于音频和视频，系统还支持上传封面图，便于在市场卡片和详情页中展示。这个设计很实用，因为音频文件本身没有可视封面，如果没有封面，市场页面会显得不完整。

平台需要提供 IPFS 存储能力。NFT 的 `tokenURI` 通常指向元数据 JSON，而元数据 JSON 再描述图片、动画、音频、视频等资源。如果直接把媒体文件存在本地服务器上，就会削弱 NFT 的可迁移性和长期可访问性。本系统后端通过 Pinata 接入 IPFS，将用户上传的媒体文件和自动生成的元数据上传到 IPFS，并返回 `ipfs://` 形式的 URI 与可浏览的网关 URL。前端拿到元数据 URI 后，再调用合约进行铸造。

平台需要提供市场浏览和交易能力。用户应当能够在首页和市场页看到当前上架的 NFT，能够按分类筛选，能够按名称、描述或 Token ID 搜索，能够按价格或时间排序。进入详情页后，用户可以查看作品媒体、名称、描述、价格、链上编号、合约地址、版税信息和历史交易记录。如果当前用户不是该 NFT 的所有者且该 NFT 已上架，则可以发起购买；如果当前用户是所有者，则可以进行重新上架、修改价格或下架操作。

平台需要提供个人中心能力。用户登录后可以查看钱包地址、用户名、头像、当前持有的 NFT、历史买入记录和历史卖出记录。项目中的个人中心将资产视图分为“当前持有”“历史买入”“历史卖出”三个标签，这样比较清楚：用户想看现在手里有什么，就看当前持有；想看交易行为，就看买入或卖出。用户还可以上传头像和修改用户名，使钱包身份具备一定平台展示属性。

在数据需求方面，系统至少需要记录用户、NFT 和订单三类核心数据。用户数据保存钱包地址、用户名、头像和 nonce；NFT 数据保存链上合约地址、Token ID、名称、描述、媒体地址、元数据地址、分类、拥有者、价格和版税信息；订单数据保存 NFT 编号、买家、卖家、成交价格、交易哈希和状态。链上是可信来源，但链下数据库承担查询、筛选、聚合和页面展示责任。两者不是互相替代，而是分工协作。

非功能需求方面，系统需要具备安全性、一致性、可用性和可扩展性。安全性要求包括钱包签名校验、JWT 鉴权、上传文件类型与大小限制、价格格式校验、合约重入保护等。一致性要求体现在链上交易成功后，后端订单与 NFT 所有者状态应同步更新。可用性要求体现在页面反馈、交易进度展示、媒体预览和错误提示上。可扩展性要求体现在模块分层清晰，后续可以加入后台管理、事件监听、多链适配或推荐机制。

三、系统总体架构设计

本系统采用典型的链上链下协同架构，可以分为表示层、业务服务层、数据持久层、区块链合约层和分布式存储层。表示层由 Next.js 前端实现，负责用户可见页面、表单、筛选、媒体预览、钱包调用和交易进度反馈。业务服务层由 Go 后端实现，负责 REST API、用户认证、上传校验、IPFS 调用、NFT 数据和订单数据管理。数据持久层由 MySQL 与 GORM 模型实现，保存用户、NFT 和订单。区块链合约层由 NFTCollection 合约实现，保存 NFT 链上所有权、上架信息、购买逻辑和版税结算。分布式存储层通过 Pinata 接入 IPFS，保存 NFT 主文件、封面文件和元数据 JSON。

从请求路径看，用户首先通过浏览器访问前端页面。若用户需要创建、购买或管理资产，就必须连接钱包并完成签名登录。前端通过 API 请求后端生成 nonce，用户在钱包中签名后，后端校验签名并签发 JWT。之后，前端可以携带 JWT 调用受保护接口。创建 NFT 时，前端先将文件和表单数据提交给后端 IPFS 接口，后端完成媒体校验、上传主文件、上传封面、生成元数据、上传元数据，然后返回 `metadataUri`、`metadataUrl`、`assetUrl`、`mediaType` 等信息。前端再用 ethers.js 调用合约完成铸造，得到交易哈希和 Token ID 后，将 NFT 基本信息同步到后端数据库。

购买 NFT 时，前端先读取后端 NFT 数据，同时读取链上上架信息和版税信息。用户确认购买后，前端调用合约的 `buy` 函数并传入准确的原生币价格。合约内部会检查 NFT 是否处于上架状态、卖家是否仍是当前链上拥有者、买家是否不是卖家、付款金额是否等于上架价格。交易成功后，合约转移 NFT 所有权，并根据 EIP-2981 版税信息进行支付拆分。前端拿到交易哈希后，再调用后端订单接口，后端创建订单并更新 NFT 的 ownerId 与价格状态。

这种架构的核心原则是：不可随意篡改且需要公开验证的部分放到链上，高频查询和复杂页面展示放到链下。比如 NFT 所有权转移、购买付款和版税结算必须在合约中执行；而市场搜索、卡片展示、个人中心排序、通知轮询等功能放在链下更合适。如果什么都上链，成本高、速度慢；如果什么都放在后端数据库，又无法体现 NFT 的可信确权价值。项目采取中间路线，是比较务实的。

前端模块按照页面和复用组件划分。`app/page.js` 是首页，展示市场概览和精选在售作品；`app/nfts/page.js` 是市场列表页，提供筛选、搜索、排序和收藏；`app/nfts/[id]/page.js` 是详情页，承担查看、购买、上架和下架等交易操作；`app/nfts/create/page.js` 是创建页，承担表单、文件预览、IPFS 上传和合约铸造；`app/profile/page.js` 是个人中心，展示用户资料、持有资产和历史订单。组件层包括 `MarketplaceCard`、`NFTTypeTabs`、`NotificationBell`、`TxProgressCard` 和 `WalletConnectButton`，这些组件把卡片、分类、通知、交易进度和钱包登录拆分出来，降低页面复杂度。

后端模块按照 config、router、handler、service、model、repository、middleware、util 分层。`router` 负责注册路由和组装服务；`handler` 负责解析请求和返回响应；`service` 负责业务逻辑；`model` 定义数据库实体；`repository` 初始化数据库；`middleware` 提供鉴权、跨域和限流；`util` 提供价格换算和文件类型检测。这样的分层虽然不复杂，但边界比较清楚，适合毕业设计项目，也利于后续维护。

四、数据库设计

系统数据库围绕 `users`、`nfts`、`orders` 三张表展开。三张表的关系并不复杂，但能够支撑平台的主体业务闭环。`users` 表保存平台用户，`nfts` 表保存平台已同步的 NFT 资产，`orders` 表保存交易记录。一个用户可以拥有多个 NFT，也可以作为买家或卖家参与多笔订单；一个 NFT 在历史上可以对应多笔订单。这里要注意，当前 NFT 的拥有者存在 `nfts.owner_id` 中，而历史流转记录存在 `orders` 中。两者一个表示当前状态，一个表示历史过程。

用户表字段包括 id、email、username、avatar、password、wallet、nonce 和 created_at。当前项目主流程已经切换为钱包身份体系，邮箱和密码字段更多是历史保留或扩展空间。`wallet` 设置唯一索引，用于保证一个钱包地址只对应一个平台用户；`nonce` 用于钱包签名登录，在生成登录挑战时写入，登录成功后清空。用户名默认可根据钱包地址前缀生成，后续用户可以在个人中心修改。头像字段保存本地上传后的 URL 或可解析资源地址。

NFT 表字段较多，因为它既要服务链上资产标识，又要服务前端展示。核心字段包括合约地址 `contract`、链上编号 `token_id`、名称 `name`、描述 `description`、封面地址 `image_url`、主媒体地址 `media_url`、媒体类型 `media_type`、MIME 类型 `mime_type`、链上元数据 URI `token_uri`、网关元数据地址 `metadata_url`、存储类型 `storage`、分类 `category`、当前拥有者 `owner_id`、价格 `price_wei` 和 `price`、价格单位 `price_unit`、版税接收地址 `royalty_receiver`、版税基点 `royalty_fee_bps`、创建时间 `created_at`。其中 `contract + token_id` 构成联合唯一索引，用来避免同一个链上 NFT 重复入库。

价格设计是本系统比较值得说明的地方。链上价格需要以 Wei 为单位，并且必须保证整数精度。如果用浮点数直接保存链上价格，很容易出现小数精度误差。因此后端使用 `price_wei` 字符串保存精确链上价格，同时使用 `price` 浮点数保存面向页面展示的 ETH 数值。也就是说，真正和链上交易对齐的是 `price_wei`，用户看到的可读价格是 `price`。这个设计虽然多了一个字段，但能同时兼顾精确性和易读性。

订单表字段包括 id、nft_id、buyer_id、seller_id、price_wei、price、tx_hash、status 和 created_at。`buyer_id` 和 `seller_id` 分别指向买家和卖家用户，`nft_id` 指向被交易的 NFT。`tx_hash` 保存链上交易哈希，便于后续追溯。项目中 `nft_id + tx_hash` 构成联合唯一索引，用于避免同一 NFT 的同一笔链上交易被重复写入。订单状态当前以 `success` 为主，说明系统采取的是“链上交易成功后再同步订单”的路径，而不是先建待支付订单再等待链上确认。

从数据库范式看，当前设计保持了较高的直接性，没有过度拆分。例如版税信息直接放在 NFT 表中，而不是另建 royalty 表；媒体信息也直接作为 NFT 字段保存，而不是单独拆出 asset 表。对于本项目规模来说，这样更简洁，也更容易和页面展示对应。若未来平台要支持一个 NFT 多个文件、多版本元数据或复杂版权声明，再拆分媒体表和版权表会更合适。

五、智能合约设计

项目中的智能合约为 `NFTCollection.sol`，合约基于 Solidity 0.8.24 编写，继承 OpenZeppelin 的 `ERC721URIStorage`、`ERC721Royalty`、`Ownable` 和 `ReentrancyGuard`。其中 `ERC721URIStorage` 提供 Token URI 存储能力，`ERC721Royalty` 提供 EIP-2981 版税支持，`Ownable` 提供合约所有者能力，`ReentrancyGuard` 用于保护购买函数，降低重入攻击风险。

合约定义了 `FEE_DENOMINATOR = 10000` 和 `MAX_ROYALTY_BPS = 2500`。BPS 是 basis points，即基点，10000 表示 100%，2500 表示 25%。在 NFT 交易中，版税比例不能无限大，否则会损害交易合理性。将版税上限固定为 25%，既保留了创作者收益空间，也避免卖家收益被过度挤压。这个上限在前端 `MAX_ROYALTY_BPS` 和后端 `maxRoyaltyFeeBps` 中也有对应校验，保持了前后端与合约的规则一致。

合约内部使用 `_tokenIdCounter` 维护自增 Token ID。每铸造一个 NFT，计数器加一，然后将新 Token mint 给指定地址或调用者。上架信息通过 `Listing` 结构体保存，包含 seller、priceWei 和 active 三个字段，并通过 `_listings` 映射以 Token ID 为键进行查询。版税基点通过 `_tokenRoyaltyBps` 保存，便于前端读取完整的版税比例，而不仅仅是 EIP-2981 返回的版税金额。

合约提供两类铸造函数。第一类是 `safeMint`，用于仅铸造不上架的场景。用户没有填写价格或价格为零时，前端调用该函数。第二类是 `mintAndList`，用于铸造后立即上架的场景。用户填写有效价格时，前端调用该函数，合约会在铸造后直接写入 `_listings`，并触发 `Listed` 事件。这个设计比较符合平台操作习惯：有些用户只想先把作品铸成 NFT，以后再卖；有些用户创建时就想上架交易。两个入口都保留，业务选择更灵活。

上架和下架由 `listToken` 与 `cancelListing` 实现。`listToken` 会检查 Token 是否存在、调用者是否为当前 owner、价格是否大于零，然后写入上架信息。`cancelListing` 会检查该 Token 当前是否上架，以及调用者是否为上架卖家，然后删除上架信息。这里的权限判断非常关键，因为只有真正持有人才能上架，只有卖家才能下架。如果没有这些检查，链上市场状态就会失去可信性。

购买由 `buy` 函数实现。该函数使用 `nonReentrant` 修饰，先读取上架信息，再检查 active、seller、owner、buyer 和 msg.value。只有当 NFT 仍然属于上架卖家、买家不是卖家、付款金额完全等于上架价格时，交易才会继续执行。随后合约删除上架信息，调用 `_transfer` 将 NFT 从卖家转给买家，再根据 `royaltyInfo` 计算版税。如果版税接收者就是卖家，则不单独支付版税；如果版税接收者有效且金额大于零，则先支付版税，再把剩余金额支付给卖家。最后触发 `Purchased` 事件。

合约还提供 `getListing`、`getRoyaltyInfo` 和 `totalMinted` 等查询函数。`getListing` 不只是简单返回 `_listings`，还会检查 Token 是否存在以及当前 owner 是否仍为 seller。如果 NFT 已经不属于原卖家，则返回 active 为 false。这个细节能避免“上架信息过期但仍被当作可买”的问题。`getRoyaltyInfo` 在标准 `royaltyInfo` 的基础上额外返回 royaltyFeeBps，便于前端详情页直接展示百分比。

合约事件包括 `Minted`、`Listed`、`Delisted`、`RoyaltySet` 和 `Purchased`。这些事件对于后续扩展很重要。如果未来加入后端事件监听器，系统可以根据事件自动同步数据库，而不是依赖前端在交易完成后回传结果。当前项目还没有真正使用后端事件监听，但合约事件已经具备基础，这说明合约设计没有只考虑当前页面调用，也为后续一致性增强留下了入口。

六、后端服务设计与实现

后端服务入口位于 `backend/cmd/server/main.go`，通过 `router.New()` 创建路由，并使用 CORS 中间件包装后监听 8080 端口。配置读取集中在 `internal/config/config.go`，支持从环境变量和 `.env` 文件读取 JWT、MySQL、Pinata 与 IPFS 网关配置。数据库初始化位于 `internal/repository/db.go`，通过 GORM 连接 MySQL，自动创建数据库并迁移 User、NFT、Order 三类模型。

路由统一挂载在 `/api/v1` 下。公开接口包括 `/ping`、`/auth/wallet/nonce`、`/auth/wallet/login`、`GET /nfts`、`GET /nfts/{id}`、`GET /orders/nft/{id}` 等。需要登录的接口包括更新个人资料、创建 NFT、更新上架信息、创建订单、查询自己的买入卖出订单、上传头像和上传 NFT 到 IPFS。这样的权限划分比较合理：浏览市场和查看详情是公开行为，创建、交易同步和个人资料修改必须鉴权。

认证模块由 `AuthHandler` 与 `AuthService` 实现。生成 nonce 时，后端先规范化钱包地址，判断是否为合法十六进制地址。如果数据库中不存在该钱包用户，则自动创建用户，并生成类似 `user_xxxxxx` 的默认用户名。随后后端生成 16 字节随机 nonce，写入用户记录。登录时，前端提交钱包地址和签名，后端用固定消息格式 `NovaNFT Login\nnonce: ...` 计算以太坊文本签名哈希，再用签名恢复公钥地址。只有恢复出的地址与请求钱包地址一致，才签发有效期 24 小时的 JWT，并清空 nonce。

这种登录流程有两个好处。第一，用户不需要记密码，身份由钱包私钥控制。第二，nonce 是一次性的，能够降低重放攻击风险。说得简单点，即使别人拿到了上一次的签名，也不能无限重复登录，因为登录成功后 nonce 已经失效。前端的 `WalletConnectButton` 将流程拆成连接钱包、获取 nonce、等待签名、创建会话四个阶段，用户知道当前卡在哪一步，体验会比一个按钮点完没反应更好。

NFT 模块由 `NFTHandler` 与 `NFTService` 实现。列表接口支持按 category 查询，也支持 listed 参数筛选已上架或未上架作品。创建接口会校验名称、合约地址、Token ID、分类、版税比例、版税接收地址、媒体字段和价格字段。分类白名单包括 art、music、video、other。版税比例不得超过 2500 bps，启用版税时必须提供合法接收地址。价格通过 `ResolveWeiAndDisplay` 统一处理，最终保存为 Wei 字符串和 ETH 展示值。更新上架信息时，后端会检查当前用户是否为该 NFT owner，避免非持有人修改价格。

订单模块由 `OrderHandler` 与 `OrderService` 实现。创建订单时，后端要求用户已登录，NFT ID 有效，交易哈希非空且以 `0x` 开头。随后读取 NFT，检查买家不能购买自己的 NFT，规范化成交价格，确定卖家 ID，然后在数据库事务中创建订单并更新 NFT owner、priceWei、price 和 priceUnit。这里使用事务是必要的，因为订单创建和 NFT 归属更新必须一起成功或一起失败。否则就可能出现订单存在但 NFT 仍归卖家，或者 NFT 已转移但没有订单记录的异常状态。

IPFS 模块由 `IPFSHandler` 与 `IPFSService` 实现。上传 NFT 时，后端要求 Pinata 配置可用，否则直接返回服务不可用。主文件最大 100MB，封面最大 20MB，请求整体最大 125MB。后端通过 `http.DetectContentType` 和白名单判断文件 MIME 类型，而不是单纯相信扩展名。图片支持 JPEG、PNG、GIF、WEBP，音频支持 MP3、WAV、OGG、FLAC、AAC 等，视频支持 MP4、WEBM、OGG、MOV 等。分类和媒体类型也会互相校验，例如 music 分类要求上传音频，video 分类要求上传视频。

媒体上传完成后，后端先把主文件上传到 Pinata 的 `pinFileToIPFS`，得到 asset CID。若是音频或视频并且用户提供封面，则继续上传封面文件。之后后端构造元数据 JSON：名称、描述、属性、文件列表和媒体类型都会写入；图片类使用 `image` 字段，音频和视频类使用 `animation_url` 字段，并在有封面时补充 `image` 字段。最后后端将元数据 JSON 上传到 IPFS，返回 asset、cover、metadata 的 URI 和网关 URL。这个过程把 NFT 创建中最容易出错的存储细节封装在后端，前端只需要关心返回结果。

头像上传模块与 NFT 上传分开。头像只保存到本地 `uploads/avatars` 目录，并通过 `/static/` 暴露。头像最大 5MB，仅支持常见图片格式。这样的划分是合理的：NFT 媒体作为资产内容，需要更持久和可验证的 IPFS 存储；头像只是平台资料，不一定需要上链或上 IPFS。功能定位不同，存储策略也就不同。

后端还实现了 CORS 和简单限流。CORS 中间件允许开发环境下前端访问后端接口，并处理预检请求。限流中间件按用户 ID 或 IP 统计请求次数，目前头像上传限制为每分钟 6 次，IPFS 上传限制为每 5 分钟 3 次。上传接口是资源消耗较高的接口，限流能减少误操作或恶意刷接口带来的压力。虽然当前限流是内存级实现，不适合多实例生产环境，但对于毕业设计原型已经能体现基本防护意识。

七、前端界面设计与实现

前端采用 Next.js App Router 组织页面，整体视觉为深色科技风格，使用玻璃拟态面板、渐变按钮、卡片悬浮效果和响应式布局。全局样式位于 `app/globals.css`，定义了背景、按钮、卡片、输入框、导航和交易状态等通用样式。项目使用 `layout.js` 统一页面外壳，包括顶部导航、移动端导航、钱包连接按钮和通知按钮。

首页 `app/page.js` 主要承担市场入口和概览展示。页面会请求已上架 NFT 列表，并计算在售数量、地板价、平均价和热门分类。首页还展示精选作品，用户可以快速进入市场或创建 NFT。这个页面的作用不是完成复杂交易，而是让用户一眼明白平台能做什么、现在市场里有什么。

市场页 `app/nfts/page.js` 承担主要发现功能。页面提供分类标签、关键词搜索、价格区间、排序和收藏筛选。排序支持最新、最早、价格从低到高、价格从高到低、名称 A-Z 等方式。收藏数据保存在 localStorage 中，属于前端本地体验功能，不影响链上和数据库状态。市场卡片由 `MarketplaceCard` 组件渲染，能根据媒体类型展示图片、视频预览或音频封面，并显示分类、Token ID、价格和版税信息。

详情页 `app/nfts/[id]/page.js` 是平台交易最集中的页面。它首先读取后端 NFT 详情和拥有者信息，再读取该 NFT 的订单历史。页面根据媒体类型决定展示方式：图片直接展示，视频用 video 控件，音频则显示封面并提供 audio 控件。同时，页面会尝试读取链上版税信息，并计算版税金额和卖家预计实收金额。用户如果不是拥有者且 NFT 已上架，可以点击购买；如果是拥有者，则可以重新上架、更新价格或下架。

创建页 `app/nfts/create/page.js` 是从链下内容到链上资产的入口。用户填写名称、描述、分类、价格、价格单位、版税基点和版税接收地址，然后选择媒体文件。页面会根据分类限制可选文件类型，并实时显示本地预览。价格输入支持 ETH、WEI、GWEI、BNB、MATIC、USD、USDT、USDC、CNY 等单位，最终通过前端换算为 ETH 和 Wei。这个功能对用户比较友好，因为很多人对 Wei 不熟，直接要求用户输入 Wei 很容易出错。

创建过程中，页面使用 `TxProgressCard` 展示 IPFS 上传、钱包确认、链上确认、后台同步和完成五个阶段。用户可以看到当前进度，也可以看到交易哈希。如果过程失败，页面会保留错误信息，并允许用户重试上次创建。这个设计很重要，因为 Web3 操作往往涉及钱包弹窗、链上等待和后端同步，任何一步没有反馈都会让用户误以为系统卡死。

个人中心 `app/profile/page.js` 展示用户资料、头像上传、用户名修改、当前持有、历史买入和历史卖出。它会并行请求 NFT 列表、已售订单和已购订单，然后根据当前用户 ID 过滤持有资产。买入和卖出记录通过后端订单聚合接口展示，包含 NFT 名称、媒体、对方用户、成交时间和价格。对于用户来说，个人中心就是资产仪表盘，不需要理解数据库表结构，也能看到自己的资产和交易状态。

钱包连接由 `WalletConnectButton` 实现。组件会检测浏览器注入的钱包，兼容 MetaMask、OKX、Bitget 等插件，并记录用户偏好的钱包类型。连接时，组件先请求钱包授权，再获取后端 nonce，再请求钱包签名，最后调用后端登录接口。登录成功后，JWT 和用户信息保存到 localStorage。组件还监听账户切换，如果钱包账户与当前登录用户不一致，会退出登录，避免用户拿 A 钱包登录后用 B 钱包操作。

通知组件 `NotificationBell` 通过周期性请求买入和卖出订单，判断是否出现新订单，并在本地生成通知。它支持未读数量、全部已读、清理已读和按买入卖出分类显示。严格来说，这不是后端推送，而是前端轮询。但就当前项目规模而言，它已经能模拟真实市场中的成交提醒体验。用户售出作品或买入作品后，不需要每次都进个人中心翻记录，顶部通知就能给出提示。

八、核心业务流程设计

钱包登录流程是系统的第一条核心流程。用户点击连接钱包后，前端检测可用钱包并请求账户授权。拿到钱包地址后，前端调用 `/auth/wallet/nonce`，后端校验地址格式，若是新钱包则创建用户，再生成随机 nonce。前端把 `NovaNFT Login\nnonce: ...` 作为消息交给钱包签名。用户确认签名后，前端把地址和签名提交到 `/auth/wallet/login`。后端恢复签名地址并比对，成功后返回 JWT 和用户信息。前端保存这些信息，后续请求通过 Axios 拦截器自动带上 Authorization 头。

NFT 创建流程更长，可以拆成链下准备、IPFS 存储、链上铸造和后端同步四段。链下准备阶段，用户填写表单并选择文件，前端检查基本输入并展示预览。IPFS 存储阶段，前端提交 multipart 表单给后端，后端校验文件大小、MIME 类型和分类规则，然后上传主文件、封面和元数据。链上铸造阶段，前端调用 `mintNFTWithWallet`，如果价格大于零则调用 `mintAndList`，否则调用 `safeMint`。后端同步阶段，前端拿到 tokenId、txHash、metadataUri 等结果后调用 `createNFT`，将 NFT 数据写入数据库。

NFT 购买流程也分成读取、确认、链上交易和订单同步。详情页先读取后端数据，确认 NFT 是否已上架，再读取链上 listing。用户点击购买后，前端调用 `buyNFTWithWallet`，该函数会校验 Token ID、合约地址、当前钱包、上架状态、卖家与买家关系，并用读取到的 priceWei 发起付款。合约完成所有权转移和付款结算后，前端拿到交易回执，再调用后端 `/orders` 创建订单。后端在事务中写入订单并更新 NFT owner。整个流程的关键是链上先成功，链下再记录，避免数据库先记账但链上交易失败。

上架和下架流程主要面向 NFT 当前拥有者。拥有者在详情页输入价格并点击上架时，前端调用 `listToken`，链上确认后再调用后端更新价格。下架时，前端调用 `cancelListing`，链上删除 listing 后，后端同步价格为 0。这里也体现出链上链下双状态问题：链上的 listing 决定真实可买状态，后端价格决定市场列表展示。只有两者保持一致，用户体验才顺畅。

个人中心流程相对简单。用户登录后进入 profile 页面，前端读取 localStorage 中的当前用户，然后调用后端接口获取所有 NFT、已售订单和已购订单。当前持有列表通过 ownerId 过滤得到，买入和卖出列表由订单接口直接返回。修改资料时，前端提交用户名或头像 URL 到 `/auth/profile`，后端根据 JWT 中的 userId 更新用户记录。头像上传则先调用 `/upload/avatar`，拿到 URL 后再更新个人资料。

九、安全性与一致性设计

安全性首先体现在身份认证。钱包登录不是简单把钱包地址提交给后端，而是要求用户对 nonce 签名。后端通过签名恢复地址，确认请求者拥有该钱包私钥控制权。nonce 登录成功后被清空，避免重复使用。JWT 中间件则保护创建 NFT、创建订单、上传头像、上传 IPFS 和修改资料等写操作。

上传安全体现在大小限制和 MIME 白名单。头像最大 5MB，NFT 主文件最大 100MB，封面最大 20MB。系统不只根据文件名判断类型，而是读取文件内容并使用 `http.DetectContentType` 识别真实 MIME，再与允许列表比对。这样可以减少用户把恶意文件改成图片扩展名上传的风险。分类和媒体类型的绑定也能减少数据混乱，例如音乐分类不应上传视频文件。

价格安全体现在 Wei 字符串规范化。链上金额必须准确，而浮点数不适合表示精确货币单位。后端通过 `NormalizeWeiString` 检查 priceWei 是否为非负整数字符串，通过 `WeiStringFromETHFloat` 将 ETH 展示值转换为 Wei，通过 `DisplayETHFromWeiString` 将 Wei 转换为页面展示值。前端在调用合约时也使用 ethers.js 的 `parseEther` 生成 BigInt 金额，避免直接用小数参与链上交易。

合约安全体现在权限检查和重入保护。上架要求调用者是 owner，下架要求调用者是 seller，购买要求 listing active、seller 有效、链上 owner 仍是 seller、买家不是 seller、支付金额等于价格。`buy` 函数使用 `nonReentrant`，并在转账前删除 listing 和转移 NFT，减少重入风险。版税支付和卖家支付都检查 call 返回值，如果转账失败则整个交易回滚。

一致性是 NFT 平台很现实的问题。链上交易和链下数据库是两个系统，天然可能出现不同步。本项目当前采取前端交易成功后主动回传后端的方式，在毕业设计原型中可行，也便于展示完整流程。但从严格工程角度看，它依赖前端完成同步。如果用户交易成功后关闭页面，后端可能没有及时记录订单。好在合约事件已经设计完备，未来可以由后端监听 `Purchased`、`Minted`、`Listed`、`Delisted` 等事件，主动校验交易回执并同步数据库。

十、测试与运行验证

从代码阅读和本次验证看，项目已经形成主要功能闭环。后端执行 `go test ./...` 能够通过，输出显示各包当前暂无测试文件。这说明后端至少可以完成编译级检查，但还没有建立系统化单元测试和接口测试。前端与合约也主要依赖人工联调和页面流程验证。对于毕业设计而言，当前验证方式可以支撑论文展示；但从工程成熟度看，自动化测试仍然不足。

建议在论文或设计说明中如实表述：系统已完成钱包登录、NFT 创建、IPFS 元数据生成、链上铸造、上架、购买、订单同步、个人中心和通知提醒等功能；后端编译检查通过；当前暂未发现独立测试用例。这样写比较稳妥，不夸大，也不回避。答辩时如果老师问测试情况，可以说明本项目采用源码检查、功能流程联调和后端编译验证为主，后续可补充 Go 单元测试、合约测试和前端 E2E 测试。

系统可验证的功能点包括：第一，钱包登录能够生成 nonce、签名、校验并签发 JWT；第二，NFT 创建能够上传媒体文件和元数据到 IPFS，并调用合约铸造；第三，市场页能够展示已上架 NFT，并支持分类、搜索和排序；第四，详情页能够展示媒体、版税、价格和历史订单，并支持购买、上架和下架；第五，购买成功后订单能够写入数据库，NFT 当前拥有者能够更新；第六，个人中心能够展示当前持有、买入和卖出记录；第七，通知组件能够根据新订单生成本地提醒。

当前系统也存在一些客观不足。第一，链上链下同步仍依赖前端回传，后端没有独立事件监听。第二，自动化测试不足，缺少覆盖核心业务的单元测试、接口测试和合约测试。第三，部分配置仍偏开发环境，例如 CORS 较宽松，JWT 默认密钥和 MySQL 默认密码需要在生产环境中替换。第四，部分文件中存在中文编码显示不一致现象，虽然不一定影响核心功能，但会影响展示质量。第五，通知功能采用轮询和 localStorage，不是严格实时推送。

这些不足并不否定系统价值，反而说明项目后续优化方向比较清楚。一个毕业设计项目最重要的是主链路跑通，结构清楚，关键技术点能解释。当前系统已经覆盖前端、后端、数据库、合约、IPFS 和钱包交互，技术综合性较强。后续如果继续打磨，可以优先补事件监听和测试，而不是盲目增加新功能。

十一、系统实现特色分析

本项目的第一个特色是链上链下分工明确。合约不承担复杂页面查询，也不保存大体积媒体；后端不替代链上所有权判断，也不伪造交易结果；前端则把两者连接起来，为用户提供完整操作路径。这种分工符合 NFT 应用的基本规律，既保证核心资产逻辑可信，又保证页面查询和交互足够顺滑。

第二个特色是多媒体支持较完整。很多 NFT 示例项目只支持图片，本项目支持图片、音频和视频，并且为音频和视频提供封面处理。元数据生成时也根据媒体类型区分 `image` 和 `animation_url` 字段，比较符合 NFT 元数据使用习惯。对数字藏品平台来说，这一点很加分，因为真实藏品不一定只是静态图片。

第三个特色是版税机制落地。合约继承 ERC721Royalty，并在铸造阶段设置版税接收地址和比例。购买时，合约按销售价格计算版税金额，再进行支付拆分。前端创建页提供版税输入和收益预估，详情页读取版税信息并展示卖家预计实收。也就是说，版税不是停留在概念层，而是贯穿了创建、展示和交易流程。

第四个特色是交易体验做了阶段化反馈。Web3 操作经常需要等待用户签名、等待区块确认和等待后端同步。项目通过 `TxProgressCard` 将流程拆开，让用户看到当前处于 IPFS 上传、钱包确认、链上确认、后台同步还是完成状态。这个看似只是界面细节，但实际能显著降低用户焦虑。普通用户不一定懂链上确认是什么，但他能看懂“现在还在钱包确认”或“后台同步中”。

第五个特色是个人资产管理形成闭环。系统不是只允许创建 NFT，也不是只展示市场。用户买入或卖出后，可以在个人中心看到资产和交易记录，顶部通知也能提醒新交易。换句话说，用户做完一次交易后，系统并没有把他丢在原地，而是提供了后续管理入口。这种闭环意识是平台类应用非常重要的部分。

十二、结论

综上所述，本项目设计并实现了一套基于区块链的 NFT 数字藏品交易平台。系统以 NFTCollection 智能合约作为链上核心，以 Go 后端作为链下业务服务，以 Next.js 前端作为用户交互入口，以 Pinata 和 IPFS 作为媒体与元数据存储支撑。通过多层协作，平台实现了钱包签名登录、NFT 多媒体上传、IPFS 元数据生成、链上铸造、上架、下架、购买、版税结算、订单同步、市场浏览、详情交易、个人中心和通知提醒等功能。

从设计角度看，系统遵循了“关键权属和交易上链，高频查询和展示下链”的原则。智能合约保证 NFT 所有权、上架状态、购买付款和版税分配的可信执行；后端数据库保证用户、NFT 和订单数据能够被高效查询；前端页面保证用户能够以较低理解成本完成 Web3 操作。这个架构既有区块链应用的可信性，也保留了传统 Web 应用的可用性。

从实现角度看，项目模块划分清晰，业务链路完整。前端页面覆盖首页、市场、详情、创建、个人中心和登录注册入口；后端接口覆盖认证、NFT、订单、头像和 IPFS；合约覆盖铸造、上架、下架、购买、版税和查询；数据库覆盖用户、NFT 与订单三类核心实体。整体来看，系统已经具备毕业设计所需的完整度和可演示性。

当然，系统仍有进一步完善空间。链上链下同步可以由事件监听增强，自动化测试可以继续补齐，生产环境配置可以更加严格，中文编码和界面细节也可以继续统一。但这些属于工程化深化问题，并不影响当前系统作为 NFT 数字藏品交易平台原型的主体成立。就目前项目来说，它已经能够比较清楚地展示区块链、智能合约、IPFS、前后端工程和数据库设计在同一业务场景中的协作方式。

如果用一句话概括本系统的价值，就是：它把 NFT 从一个孤立的链上 Token，扩展成了一个可登录、可创建、可展示、可交易、可追踪、可管理的完整平台流程。这个流程既能体现区块链技术的可信确权优势，也能体现软件工程中模块分层、数据建模、交互设计和业务闭环的重要性。因此，本系统具有较好的毕业设计展示价值和后续扩展基础。
